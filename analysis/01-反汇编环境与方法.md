# 01 · 反汇编环境与方法

- **证据文件**：`cve-2026-43499-app.so`（SHA-256 见 `hashes.md`）
- **工具**：AArch64 `objdump`、`nm`、`strings`、自写 Python 脚本
- **关键地址**：见各篇

## 1. 为什么要在沙箱里拆

设备上没有稳定的分析工具链，且 payload 是 AArch64 静态 `.so`，
所以做法是：把 payload 复制到沙箱 → 用交叉工具链 objdump 反汇编 → 落成 `.dis` 文本再检索。

产出的中间文件（均在 `/home/rmg`，非仓库内容，仅列名备查）：

| 文件 | 大小(B) | 用途 |
| --- | --- | --- |
| `pl.dis` | 429131 | payload 全量反汇编 |
| `prep.dis` | 31500 | `prepare_kernel_page` 附近片段 |
| `fc.dis` | 11612 | `find_collisions` 附近片段 |
| `refs.out` | 11754 | 交叉引用（谁调用谁） |
| `xr.out` | 2975 | 额外交叉引用 |
| `strva.json` | 344 | 字符串 → 虚拟地址 映射 |
| `pairs.out` | 721 | 关键"字符串-地址"配对 |

## 2. 基本命令

```sh
# 反汇编（AArch64）
aarch64-linux-gnu-objdump -d --no-show-raw-insn cve-2026-43499-app.so > pl.dis

# 只看某个函数范围（按 VA 起止）
aarch64-linux-gnu-objdump -d --start-address=0xd014 --stop-address=0xd4e4 \
    cve-2026-43499-app.so

# 字符串 + 偏移
strings -a -t x cve-2026-43499-app.so | grep -nE 'SLIDE_ONLY|P0_ONLY|KSNITCH'

# 符号表
nm -D --defined-only cve-2026-43499-app.so
```

## 3. "字符串地址 → 代码引用"的找法

要回答"这个环境变量在哪被读取"，流程是：

1. `strings -t x` 拿到字符串的文件偏移（例如 `SLIDE_ONLY` @ `0x8b74`）。
2. 在 `.dis` 里搜这个 VA 的加载指令（AArch64 常见为 `add xN, xM, #imm` 或 `adrp+add` 组合）。
3. 找到引用点后，向上回溯到函数入口，用 `nm`/符号或调用图确认函数名。

> 注意：这里的偏移是**文件偏移**还是**虚拟地址**要分清。本 payload 中
> 根据上下文判断字符串偏移与 VA 一致（静态、无重定位偏移），
> 因此 `@0x8b74` 这类可直接当 VA 用。若换文件需重新验证。

## 4. 已知的找法收益（本轮）

| 目标 | 结论 |
| --- | --- |
| 找碰撞阈值判断点 | 命中 `d288-cmp` / `d28c-bne` → 见 `02` |
| 找扫描参数来源 | 硬编码于 `ee00–ee08`，无 getenv → 见 `02` |
| 找隐藏诊断开关 | 命中 3 个 env → 见 `02` |
| 找 futex 哈希实现 | 命中 `cb54/cc1c/cc64/cc44` → 见 `03` |

## 5. 局限与风险

- 反汇编是**静态**的：只能说明"代码里这么写"，不能证明运行时一定走到这里。
  运行时的证实要靠日志（`RootMyGalaxy-*-failed.log.txt`）。
- 交叉引用靠手工+脚本，可能有遗漏：**未命中 ≠ 不存在**。
- 结论随时可能被新的反汇编或运行时证据推翻，届时应新增分析文件而非改旧文。
