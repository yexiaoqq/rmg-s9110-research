# 04 · 上游 5.15 参数档对比

- **证据来源**：上游 PR #462（5.15 专用参数分支）、PR #375、PR #613、支持矩阵
- **工具**：GitHub API 拉取的 PR diff / 评论
- **用途**：判断“我们的失败是不是被过早掐断”

## 1. 核心发现

上游在某个 PR 中引入了**按内核版本分支**的超时/尝试参数。
分支键是 `kernelVersion.startsWith("5.15")`。

| 参数 | 默认档（我们实际在跑） | 5.15 专用档（上游给） |
| --- | --- | --- |
| `EXPLOIT_ATTEMPTS` | 24 | 8 |
| `P0_ATTEMPT_TIMEOUT_SEC` | 45 | **1200** |
| `EXPLOIT_ATTEMPT_TIMEOUT_SEC` | 120 | **2200** |
| `EXPLOIT_STALL_MILLIS` | 90 s | **180 s** |
| `EXPLOIT_TOTAL_MILLIS` | 15 min | **60 min** |

**量级差距**：单次 attempt 超时，默认档 120 s，5.15 档 2200 s —— 差 **约 18 倍**。

## 2. 与我们的实测对照

我们的失败日志显示：

```
preload supervisor pid=10770 attempts=24 base_delay=20000 p0_timeout=180 timeout=480
...
exploit attempt=1/24 timeout pid=10771 seconds=180
```

- `attempts=24` → 走的是**默认档**。
- 单次实际 **180 s** 就被 SIGKILL，然后进入下一次 attempt，24 次空转约 50 分钟。

**推论（重要）**：如果 5.15 真的需要 2200 s 才能走完一次 attempt，
那么我们用 120/180 s 的档，**很可能每次都在“即将出结果前”被掐断**。

> [推测] 失败原因可能不是“走不通”，而是“跑不完”。
> 反例风险：也可能是 5.15 档的长超时只是为了容忍更慢的机器，
> 而我们在 180 s 内已经确定性卡在同一行（`dma32_skip=8` 之后），
> 属于**真卡住**而非**被掐断**。两者需通过分阶段实验区分。

## 3. 为什么这个发现很关键

1. **不需要改二进制**：超时是**运行时环境变量**，可在 shell 域带自定义 env 手起 payload 验证。
2. **反馈快**：不必重打包 APK、不必重装。
3. **可逆**：改错了只是多等一会儿，不改变内核状态。

因此这是**下一步优先验证项**（见 `journal/2026-10-02-002` 的“下一步”）。
