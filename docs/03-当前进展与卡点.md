## 2. KASLR 泄露：已经跑通的部分

- 路线：读内核 **tracefs** 中的 `sched_blocked_reason` 事件。
- 事件 id = 108，caller 偏移 16，每条 36 字节。
- 捕捉到裸指针 `0xffffffc008155b44`。
- 日志显示：`slide-kaslr-ok base=ffffffc0081d0000 slide=0x1d0000`。

**结论：知道内核这次被摆在哪了。**

## 3. 异常重启（panic）根因：SELinux 域问题

早期的 panic 并不是算法算错，而是：

> 进程以 **`untrusted_app`** 身份去读 tracefs，被 SELinux 拒绝（`errno=13`），payload 于是**降级走 physical P0**，最终导致复位。

这就引出了一个关键点：**身份不同，能做的事不同**。
- `untrusted_app`（普通 App）：不能读 tracefs。
- `shell`（Shizuku 给的身份）：可以。

所以在“带自定义环境变量重跑验证”时，应优先在 **shell 域** 下手起 payload，而不是全靠 App 内发起。（App 内也提供了一个“使用 Shizuku”开关来改变发起身份。）

## 4. 卡点详细：页碰撞只找到 0～3 个

### 4.2 从日志能读出什么

1. payload **越过了 search 行**，进入了碰撞扫描——**不是死锁**。
2. 它在 `controlled mm group` 阶段只凑出 **0 个碰撞**。
3. 所有 attempt 都是在 **`untrusted_app`** 域启动的。
4. 单次 attempt 实际给了 180s 就被掐断（`timeout`）。

### 4.3 已经排除的猜测

| 猜测 | 结论 | 证据 |
|---|---|---|
| 进程被 OOM 杀 | ❌ 排除 | supervisor 与 attempt 进程 90s 后仍存活 |
| futex hashsize 算错 | ❌ 排除 | 本机 nproc=8 → 8*256=2048，与内核一致 |
| 卡在“扫描”死循环 | ⚠️ 部分：会停在 `controlled mm group search scans=256 objects=32 dma32_skip=8` 很久，但最终会超时退出 | 见日志 |
| FUTEX_WAKE 短临界区可区分同桶/异桶 | ❌ 实测无可测差异 | 多轮受控实验，`delta_med` 全为 0 |

### 4.4 目前最可能的两个方向

1. **超时太短**：上游在 5.15 分支上把单次 attempt 超时提到 **2200s**（默认档只有 120s），提示我们可能是“还没做完就被掐断”。
2. **grooming 策略（reclaim）不适合 5.15**：上游公开矩阵里 `android13-5.15 = Untested`，很可能就是 reclaim 策略在这一分支上表现不同，导致碰撞凑不够。
